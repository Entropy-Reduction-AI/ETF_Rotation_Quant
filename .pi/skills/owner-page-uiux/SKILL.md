# 面向 Owner 的页面：规范、组件与发布门

仓库 Entropy-Reduction-AI/ETF_Rotation_Quant 里有一套已经定下的 UI/UX 规范。做任何面向 Owner 的页面，**动手之前先读规范，发布之前必须过发布门**。不要凭感觉设计，也不要只看 md 文件就开始转。

**核心：每个元素都是讲故事的人（Owner 十几轮评论反复强调）。** 页面不是把内容排整齐，而是讲一个故事。判断标准只有一个：Owner 不读正文、只看视觉重点，能不能讲出这一节的结论。讲不出来就没做完——lint 没报错也不算。“草稿”“合同”“只是排版”都不是降低标准的理由：草稿页正是 Owner 审稿的地方。

## 0. 开工前必读（按顺序）

1. `docs/reference/owner-facing-uiux-principles.md`：全文，尤其第 0、0.1、13 节和 13.x“先图后表”。
2. `docs/reference/owner-page-story.css`：组件样式（`.memo`、`.vd-card`、`.cards3`、`.ib`、`.big`、`tr.grp`、`.lt`、`.rn`、`.tag-a`、`.stk`）。
3. `scripts/owner_page_lint.py`：发布门的自动检查，0 个 ERROR 才允许发布。
4. `AGENTS.md` 第 5 条（每个面向 Owner 的产出都是讲故事的人）。
5. `docs/reference/owner-page-story-patterns.md`：从预测表 3.0–3.22 提炼的模式库——一节的标准骨架、每个组件靠什么 md 写法触发、合同类文档怎么改写。**新页面先对照这份清单改写源 md，再生成。**
6. 要转换的源文档（`docs/owner/*.md`、`docs/prereg/*.md` 等），以及它引用的所有配图 `docs/assets/**`。

## 1. 不可违反的底线

- **内容一条不删。** 源文档的每一句、每张图、每张表都要出现在页面里（只有 Metadata 不搬）。次要内容可以进折叠区，不能消失。转换后逐行核对正文、数图片张数。
- **不编内容。** 颜色、框、结论只能来自源文档本身（作者的加粗、结论列、正文里明说的“框出的/标橙的”）。推不出来的，如实告诉 Owner，不硬猜。
- **版面要宽。** 用独立 HTML 页面（宽主栏约 960–1200px + 左侧目录），不用窄栏文档类型；原文的宽幅图必须能看清。

## 2. 每一节 = 一条证据链（第 13.2 节）

1. 标题 = “问题：结论”，结论里有方向。
2. 记忆句 `p.memo`：一句话，带决定结论的一两个数字。
3. 证据元素：**每节必须有一个证据视觉**（图、步骤表、计分条、情形卡、焦点表）。有数据先放图，图的标题就是结论；明细表放进“明细表”折叠；一节最多展开一张表。没有证据视觉的节要写明为什么不需要。
4. 读法：最多三条，每条以加粗短语开头；第一条通常是“读这张图”，紧跟在图后面。
5. 需要的话，一句“下一节接什么”。

## 3. 元素规则

- **顶部状态**：`section.status`，三格（进度 / 结论 / 需要你），回答“现在怎样、要我做什么”。
- **表格**：
  - 列序 = 阅读顺序：名字 → 证据（数字、条）→ 原因（短语）→ 结论（标签）。
  - 必须有结论列，用标签（赢 / 输 / 兑现 / 不可用），不是长句。
  - 每一行在名字以外的格子里要有视觉重点：上色数字、标签、内联条 `.ib`、大数字 `.big`。
  - 整张表只框一两格：决定标题结论的那一格。整列都上色等于没有信息。
  - 单元格是短语（约 46 字以内）；长理由放表下或折叠区。
  - 长表用分组行 `tr.grp`，分组行本身就是小结论。
  - 名词表、清单表标 `data-lint="ref"`。
  - 代码路径、PR、SHA 不进正文表格，放“工程用”折叠区。
- **颜色语义全站统一**：绿 = 比参照好，橙 = 比参照差，框 = 决定结果的格子，标签 = 状态。同一版本在所有图里颜色相同。
- **正文**：不写没有加粗的大段文字；超过两行就拆成“加粗短语 + 解释”或卡片。判断类内容用结论卡片 `.vd-card`（大字结论 + 一两句证据 + 出处）。
- **列表项**：都以加粗短语开头。
- **选项**：带建议的选项用卡片，推荐项高亮，写清每个选项的代价。
- **折叠区**：`div.fold > button.fold-h[aria-expanded] + div.fold-b`，必须实测能点开。
- **深色模式和窄屏（约 400px）**：都要检查。

## 3.5 焦点：每个大元素都要讲一句话（2026-11-17 评论轮次的硬要求）

Owner 的标准是：**“加粗 + 纯文本”不合格**。每一个大元素（页首、表、卡片组、步骤、清单、总览）都得回答“看这里先看什么”，而且焦点只能取自源文档本身。下面这些组件已经在 `gen/story.py` 里实现，新页面直接套用：

- **页首（`section.status`）= 结论在前**，不是三张一样大的卡片：
  - 结论卡最大，第一句做大字标题，其余作为灰色证据。
  - 能画的就画：拿“策略 X% vs 基准 Y%”画对比条；“N 个起点 K 个赢”画 N 个圆点，赢的实心。
  - “需要你”单独放进蓝框：动词放大，事项拆成 ①②③ 清单；“不用操作”显示成绿色 ✓。
  - 进度降成一条细状态栏（✓ + 一句话）。
  - 愿景收成一行，目标加下划线，方便和结论对照。
- **步骤流（4 步规则等）**：
  - 每张卡分三层：小灰字步骤名 → 大号焦点短语 → 原文解释。
  - 焦点取作者在这一步的加粗；没有加粗，就取这一步的收尾短句。
  - 每一步都取得到焦点才启用，四张卡的焦点连起来就是故事线。
- **决定记录（D 编号表）**：
  - 顶部放一条按编号排序的时间线，节点能跳转；最新的一条标“最新”。
  - 每张卡左栏：编号、名称、几条；右栏：大号核心句。
  - 每条决定前加语义图标：✓ 规则 / ! 约束（只、不、推迟）/ ⇄ 替换旧做法（“不用 X”给 X 加删除线）/ ↻ 改动（“改为”标成旧 → 新）/ ★ 结果（“只有 X 能…”给 X 绿色高亮）。
- **接下来（行动表）**：
  - 顶部一排计数：待你拍板、等你之后、待做、已完成、持续、排队。
  - 你的事项放进蓝框，做成编号决定卡，动词放大；“A，或 B”拆成两个选项标签。
  - 其他人做成并排小卡；每条带状态标签：✓ 已完成 / ⏳ 等你拍板（正文写着“你定了…后”）/ → 待做 / ↻ 持续 / 排队。
  - D 编号、PR 号做成编号标签。
- **折叠区的“这一段讲了什么”总览**：做成故事卡片，不要列表。每张卡：
  - 编号 + 结论标签（问题 / 有效 / 成立但有代价 / 背景），卡片顶边用同色；
  - 放大的关键数字，从结论句里抽：A → B、A vs B、A … B、涨/跌两数；
  - 结论原文，数字高亮。
  - 没有结论句的小节，改成带编号的跳转标签，不留空卡。
- **表格（`table_focus`，对所有表生效，包括 `data-lint="ref"`）**：
  - 有“基准”列：每个数字和同行的基准比。好于基准绿底，差于基准橙底；回撤、波动、跟跌、换手这类按“越低越好”。
  - 表头决定列的角色：
    - 结论 / 判定 / 本该得出的结论 → 左侧强调线，字体加重；
    - 为什么 / 证据 / 做了什么 → 灰色小字；
    - 代价 / 反面证据 / 超出就要查 → 橙色，表头加 ⚠；
    - 状态 / 可信度 → 状态标签；
    - “第 2 版 | 第 3.2 版”、“上一轮 | 这次” → 旧版灰、新版高亮，表头加 →。
  - 行首的 a/b/① 编号做成小方块。
  - 2–4 种取值的短分类列（设计前 / 设计期 / 检验前）做成彩色小标签。
  - “同上”换成上一格的标签（半透明），下面留“同上”两字。
  - 表头是“会不会变慢”这类问题时，“不会 / 会”做成好 / 差标签。
- **案例段落**：连续几行“X：一句话结论”、每行后面跟着正文的，做成并排的案例卡。X 做成标签，结论放大，按语义上色。
- **源文档里的行内子弹**（一行里有多个 `* `）：拆成子要点；有“A：”的，A 加粗。
- **自查脚本** `gen/audit.py`：列出没有任何视觉重点的表、没有数字或标签的卡片组、连续三段以上的纯段落、没有样式的长列表。清零或逐条说明，才算“自己审过”。

## 3.6 讲故事层：焦点由作者写进 md（2026-11-24，v6 预注册 2.2 版）

根因：生成器从条款原文里“猜”焦点，猜出来的是样式不是观点。合同类、规则类文档一律在 md 里写故事层，生成器（`scripts/owner_pages/story_layer.py`）只负责摆放：

- `<!-- 问：……｜短：两三个字｜状态：已定 / 待你定 / 待补 -->` 紧跟每个 `##`：标题下“这一节回答”，并生成页首故事主线。
- `<!-- 看点：一句话｜框：格子里的字 / 另一个 -->` 紧贴每个表、卡片组、图、定义格、步骤流的上方。看点说几个数就框几个；图里框不了就点名“看哪根柱、哪个数”；数字和标题、一句话答案一致。有 `<!-- 页面：卡片 -->` 时，看点写在卡片标记之前。
- `<!-- 接力：…… -->` 每节最后一行：说清这一节的结论为什么把读者带到下一节。
- `<!-- 页面：定义 -->` 放在“**名词**：规则……”列表上方，变成名词 / 规则 / 出处三栏；`<!-- 页面：参考 -->` 只给查阅表用。
- 同组卡片按看点分组；卡片标题用加粗短语，结论放大，不重复。

## 3.7 形式跟着内容走（2026-11-24，v6 预注册三轮；取代“每个元素上方加一句看点”的做法）

Owner 给的标杆是《v6 预演预测表》，做对的是四件事：

1. **展开前的信息熵集中**：不点开折叠时看得见的每个元素都是高信息量的数字或结论；铺垫句、重复句、条款原文一律进折叠。参照：预测表全页不展开约 5,900 字、每节中位约 430 字。
2. **同一节的几张表用不同形式**：按内容本身的结构选形式，不拿一个通用组件套所有节。
3. **折叠里的明细表素净，但不是平铺**：不加看点条、框和多余颜色；可展开后的内容同样要按内容选形式（见 3.8）。只有“按行查”的纯清单才保留表格，而且要分组、把重复值提到表上方。2026-11-25 的 45 条评论里，一半是冲着折叠里的平铺表和“加粗 + 纯文本”来的。
4. **表上方的小视觉**：对比条 / 计数条、副标题高亮。

每节默认视图 = 标题 + 一句话答案 + 一个按内容选的视觉 + 折叠里的条款原文 + 一行接力。组件在 `scripts/owner_pages/components.py`，md 里写 `<!-- 组件：名称｜标题 -->` 加一张小数据表：

| 组件 | 内容的结构 | 例 |
| --- | --- | --- |
| 分拣 | 一组条目按结论归类 | 已经看过的信息 |
| 闸门 | 几道必须全过的门槛 + 事先机会 | 判据 |
| 构成 | 几个组合的成分比例 | 基准 |
| 计数 | 一组东西按类别计数 | 常数来历、陷阱类别 |
| 路线 | 有先后、有“现在在哪一步” | 冻结流程、上线路径 |
| 退路 | 条件不满足就往下一档退：横排逐级下沉的台阶，每级上方写退到这一级的条件 | 买哪只基金（竖排阶梯加虚线、橙色胶囊被评“难看”） |
| 载体 | 一组名字按类型分行（芯片） | 候选清单、通过/不通过 |
| 代价 | 按来源分组；只把代价的数字放大，前缀缩成灰字；代价和警戒线单位相同时画刻度条（代价块 + 红线 + 越线区） | 疼痛表 |
| 风险 | 有先后顺序的几条风险：列头“原因 / 会怎样 / 在哪里盯”，第 1 名红底、第 2 名橙边 | 红队 |

- 组件里的每个数字和名称，都要能在折叠里的条款原文或附表里找到（R1b 会逐行溯源；把正文句子删掉、只留在组件里，会被判“无出处”）。
- 可见表只框唯一决定性的格子：`<!-- 框：格子文字 -->`。
- 组件容器用 div，不用 ol/li：生成器会把列表项包一层 <b>，弄乱网格。
- 问句（`<!-- 问：… -->`）只进页首故事主线，不再在标题下多一行；接力（`<!-- 接力：… -->`）保留。

## 3.8 冻结文档与“每一块都按内容选形式”（2026-11-25，v6 预注册评论三轮，约 45 条）

**冻结后 md 一字不能动**，页面上的所有改动都做在生成器里：`scripts/owner_pages/forms.py` 按**表头签名**（或定义名词、折叠标题）识别一块内容，换成对应形式；认不出就原样保留。不往正在复核的 PR 分支推（会改掉 Reviewer 签收的头），另开分支。冻结后页面加一条“已冻结”横幅、标题改“已冻结”（`build.py` 的 `FROZEN`），并说明条款里的“待冻结”是冻结时的原话。

形式目录（内容是什么结构 → 用什么）：

| 内容 | 形式 |
| --- | --- |
| 每月几步的规则 | 步骤行：问题大字；“三票”拆成票卡；“不紧张 / 紧张”拆成状态卡；“…时，…”做成例外条；原文加粗句做结果标签 |
| 一个算式（把握 p） | 三步算式条：记下 → 算 t → 换成 p，下面一行写各自从哪里起算（照抄预测表的 calcgrid） |
| 两条规则对照 | 并排两列，行名下标“相同 / 不同 / 地位”，不同的格子铺浅底 |
| 常数来历 | 按“看过数据后定 / 文献 / 约定”分组，取值放大 |
| 规则明细 | 规则名做标签；取值里决定性的量加底色；代价单列 ⚠ 浅橙条；来历标签靠右 |
| 编号规则清单 | 等宽规则卡：编号 + 规则名 → 原文加粗句做大字 → 原句灰字 |
| 问答清单 | 问答卡：第一句回答放大，“已写入：…”做绿标签 |
| 情景画像 | 情景卡：顶色按好坏，例子放灰框、日期加粗；“约八成 / 六成”这类判断画成概率条 |
| 已看过的信息 | 每条一卡：结论标签 + 加粗句做标题 + 一行“影响”，细节收进卡内 `<details>` |
| 基准 / 构成 | 成分比例条；首次出现的术语（K2A）在卡内补一段解释，取自决定记录并注明出处 |
| 对照组 | 分“同结构 / 外部只报告”两组，用“回答什么”做标题，长口径收进“完整口径” |
| 判据 | 和上方的图一一对应的卡：门槛大字 + 事先机会（取自同节闸门）；来历里的 D 编号改成说人话（“你 11-17 定的回撤底线”），编号缩成灰色小字 |
| 时间轴 | 节点带编号，已完成 ✓；“之后”降为灰字，只有“现在 / 你批准”用彩色标签；每步下面一行写这一步靠什么定，原句取自本节条款 |
| 性质不同的条款 | 按性质分排：主线 + 暂停线、影子（虚线、只记录）、只报告（虚线、蓝顶） |
| 陷阱 / 风险清单 | 卡头类别标签，卡身“会怎样 / 怎么处理”两行 |
| 待办 | 完成卡 + 顶部“8 / 8 已完成”进度条；“已完成（日期）”拆成日期标签 |
| 逐年数据 | 每个名额一块：12 个月格涂色、仓位画条，其余小字靠右 |
| 排名次数、净值序列 | 条形标签 / 条形 + 对基准的差（绿高橙低） |
| 长明细清单 | 按分类分组，重复值（口径、截止日）提到表上方只说一次 |

- **粗体只给数字和决定**：情形名、事项名用中等字重；“每年少约 9 点”只放大“9 点”。Owner 的原话：“大部分的 Bold plaintext，太糟糕了”。
- **焦点来自源文档**：标签、标题、门槛一律取原文（加粗句、结论列、条款原句）；补进来的解释要能在决定记录里找到并注明。

## 4. 发布门（必须走完，不能跳过）

1. **自动检查**：`python scripts/owner_page_lint.py <page.html>`，0 个 ERROR；WARN 逐条看，能改就改。
2. **内容核对**：源文档逐行对照页面（去掉 Markdown 记号后做子串匹配），图片张数一致，无 `**`、`~~` 残留。
3. **逐节截图**：每节单独截图，写下 ① 标题的结论是什么；② 5 秒内能从哪个元素看到它；③ 视线先落在哪、再去哪。答不出 ② 就改。
4. **整篇通读**：只读标题和记忆句，能不能连成一个完整故事。
5. **逐屏看完整页**：先展开所有折叠区、等图片全部加载完再截图；不能只看一部分就说“审完了”。
6. **跑 `scripts/owner_pages/audit.py <页面目录> [slug…]`**：它从 `build.py` 读页面清单（新页面不会再漏查），报告没有焦点的表、纯文本段、**没有证据视觉的节（NOVIS）**；再对它们单独截图（`scripts/owner_pages/el.py out.png 'slug|selector|idx' …`）。
6.5 **焦点下限**：新页面的 lint WARN 数和 audit 缺口不能比《v6 预演预测表》多（参照值：WARN 6、缺口 2）。多出来的逐条改；合同条款原文造成的长格可以保留，但要在发布说明里逐条列出。
6.6 **改了生成器，就对其他页面做正文对比**：用改前、改后的生成器各建一次，比较 `<main>` 的内容；除样式和页脚外有任何差异，先收窄触发条件（例：首词分类标签曾把数字列和带链接的格子变成标签，被对比抓出来）。
6.7 **讲故事层门**：`python scripts/owner_pages/story_check.py <page.html> --digest 连读稿.md`，0 个 ERROR（问 / 接力 / 看点 / 框 / 卡片标题重复 / 折叠外长段落）；连读稿两分钟能读成一个完整故事。
6.8 **冷读测试**：逐节截图（折叠全展开），交给没看过源文档的独立 agent，只回答：这一节的结论、视线先落哪、哪个元素读不出要点或看点与框对不上、接力是否成立。列出的问题清零或逐条说明再发布。
6.9 **默认视图门（`scripts/owner_pages/story_check.py <page.html> --digest 连读稿.md`）**：DENSE，每节不展开 ≤ 700 字；FOCUS，每节在折叠外有一个视觉；CLEAN，折叠里不出现看点条和框；NEXT，每节有接力。0 个 ERROR 才发布。先用它量一遍参照页（预测表）再定目标。
6.10 **冷读测试**：逐节截图（折叠不展开）加参照页截图，交给没看过源文档的独立 agent：每节 5 秒结论、第一眼落点、哪个元素信息密度低或形式不贴内容、估计 Owner 接受度。列出的问题清零或逐条说明。
7. **改了公共组件，就重建并检查所有页面**：同一个类可能出现在别的页（例如 `.actboard` 也在 v4 体检报告里）；只发布实际变化的页面。
8. 第 12 节的八条照旧。

## 5. 发布

- 用 artifact 发布（`publish_files`，index.html + assets/）。页面之间的链接互相指向新 artifact；仓库内文件链到 GitHub。
- 改版时页面、仓库 md、项目空间三处同步（规范第 10 节）。

## 5.5 处理 artifact 评论

- 改动做在生成器里（`gen/story.py` / `gen/polish.py`），不要手改 HTML，否则下次重建就丢了。
- 先重读评论锚点指向的那一节当前的 HTML，再动手。
- 改完：lint 0 ERROR → 内容核对 → 截图 → 发布 → 在评论线程里回复。回复写清改了哪几层、焦点来自源文档的哪里、还有哪些页面一起改了。
- 会话里只写一句话。线程留给人来关，不自己 resolve。
- Owner 会一口气留十几条评论，之后还会逐条重发：每次先读全部线程，把所有“等回复”的一起改完、一起发布，再逐条回复；重发的、已回过的，会话里只说“已处理，回复在线程里”。
- 回复写三件事：原来的问题、现在的读法（从上往下 / 从左往右看到什么）、哪些页面跟着变了。

## 7. 教训（2026-11-17，评论轮次）

- Owner 连续 10 多条评论都是同一个问题：**元素有样式但没有焦点**。每个元素都要回答三件事：看哪里、为什么、和前后什么关系。只有加粗、圆点、边框不算焦点。
- 焦点必须来自源文档：作者的加粗、结论列、和基准的比较、正文里的“不用 / 改为 / 只有”。不要发明评价。
- 上色要按方向，不按页面整体情绪：结论不通过，并不意味着页面里每个数字都标红（24.9% 对 15.6% 仍然是好）。
- 改生成器时留意变量作用域：循环外用了上一轮循环的变量，导致整列显示同一个数（4.0%）。截图里出现“整列一样”，先怀疑这个。
- 数字格式化不能改动原值：4.0% 不能变成 4%，“年化”的“年”不能被数字标签吃掉。
- 嵌套 wrapper 可能带来解释不清的偏移；能用 grid-area 直接排，就不要多套一层。

## 8. 教训（2026-11-23，v6 预注册初稿）

- 预注册页面只做了“排版过 lint”：0 个 ERROR，但 57 个 WARN、10 节里 0 节有证据视觉，和十几轮打磨过的预测表差得很远。根因有三：只把“0 ERROR”当完成；`audit.py` 的页面清单写死、根本没查这一页；预测表的能力只存在于那一页的写法里，没有变成可复用的流程。三处都已修：发布门加焦点下限、audit 自动读页面、模式库成文。
- **合同类文档（预注册）条款一字不改，讲故事全靠结构**：标题下加“条款的读法”步骤表（声明以折叠里的条款原文为准）；沿用已发布页面的同一张图（“原样进入”的内容不另画）；表格加短语列（结论 / 门槛 / 状态）再做成情形卡；长理由移到表下或折叠。
- **新组件：情形卡**（`ledger_cards`）。表头有“超出…”列或第一列是“陷阱”时自动触发；其他表在表前写 `<!-- 页面：卡片 -->`。代价 / 结论 / 状态 / 门槛列做大字，最后一列做卡底（“超出”显示 ⚠ 红色）。
- **新图只照抄正文数字**：每张图的脚本注明数字出处；画完核对标题里的数（预注册附表 A 的“设计期末 35 个”实算是 34 个，标题当场改正）。
- **步骤卡的焦点要写在 md 里**：`1. **步骤名**：……**焦点短语**……`；焦点没加粗时生成器会取收尾短句，常常取错（§2 第 3 步曾显示“再不行给母指数”）。

## 9. 教训（2026-11-24，v6 预注册三轮：接受度 40% → 约 70% → 继续打磨）

- **第一轮的错**：给每个元素加一句“看点”（全页 43 条）。焦点还是文字，默认视图从 13,056 字没降下来；检查只核对“有没有看点”，没核对“第一眼要读多少字”，所以全过却仍是一堵墙。**先把“太多字”变成能量的数，再设门。**
- **第二轮的错**：用一个通用组件（要点格、精简卡片）套所有节。Owner：同类内容要按内容换布局。**先问“这段内容本身是什么结构”（分类？门槛？比例？先后？退路？代价对警戒线？），再选组件。**
- **第三轮的错**：疼痛表做成普通三列表，八种情形读不出轻重和来源。改成按来源分组、代价大字、警戒线红字。
- **数字要一致**：标题说“4 项”、组件说“6 项”、正文“+5.0”、图上“+4.3”这类不一致，冷读一眼就抠出来；写组件时对着标题和图核一遍。
- **同一张表不要拆成几张**：折叠里的原文合成一张、按编号排；分组交给可见的组件。

## 10. 教训（2026-11-25，v6 预注册评论三轮）

- **CLEAN 门理解反了**：上一轮把“折叠里素净”做成了“折叠里平铺表”，Owner 逐块打回。素净是指不加看点条和框，不是不排版；展开后的每一块也要 3 秒看出重点。
- **自审标准换成 Owner 的标准**：每块单独截图（折叠展开），问“如果 Owner 只看到这一块，3 秒内看得出重点吗？是不是一排粗体 + 灰字？”。答不出就换形式，而不是加颜色。
- **评第二次的地方，多半是形式没选对**：退路从横排卡片 → 竖排阶梯 → 逐级下沉的台阶；时间轴第二轮补编号和每步的判定条件。第二次改时先换形式，不在原形式上加装饰。
- **生成器的坑**：
  - 表头字号比行小、列宽用 em，就会错位：列宽用 px，或把字号放到子元素上。
  - `story.py` 会给 `ol` 加 `flow / steps-n`、给 `li` 包 `<b>`：组件用更高优先级覆盖，或者干脆不用 ol。lint 要求列表项以粗体开头，组件里的 li 自己包一层 `<b>`。
  - `polish` 会把数字包成带底色的 `.num`：大数字场景要覆盖。
  - `el.py` 截图写到仓库 `shots/`：已加进 `.gitignore`，提交前确认没带进去。
  - 签名识别前先 grep 所有页面，确认同一表头没有在别的页被误改。
