# 面向 Owner 的页面：规范、组件与发布门

本仓库已有一套定下的 UI/UX 规范。做任何面向 Owner 的页面，**动手之前先读规范，发布之前必须过发布门**。不要凭感觉设计，也不要只看 md 文件就开始转。

## 0. 开工前必读（按顺序）

1. `docs/reference/owner-facing-uiux-principles.md`：全文，尤其是第 0、0.1、13 节和 13.x“先图后表”。
2. `docs/reference/owner-page-story.css`：组件样式（`.memo`、`.vd-card`、`.cards3`、`.ib`、`.big`、`tr.grp`、`.lt`、`.rn`、`.tag-a`、`.stk`）。
3. `scripts/owner_page_lint.py`：发布门的自动检查，0 个 ERROR 才能发布。
4. `AGENTS.md` 第 5 条：每个面向 Owner 的产出都是讲故事的人。
5. 要转换的源文档 `docs/owner/*.md`，以及它引用的所有配图 `docs/assets/**`。
6. 现有页面和生成器：`docs/artifact/README.md`（页面清单、怎么重建）和 `scripts/owner_pages/`。

## 1. 不可违反的底线

- **内容一条不删。** 源文档里的每一句、每张图、每张表都要出现在页面上，只有 Metadata 不搬。次要内容可以放进折叠区，但不能消失。转换后要逐行核对正文，并数一遍图片张数。
- **不编内容。** 颜色、框、结论只能来自源文档本身：作者的加粗、结论列、和基准的比较、正文里明说的“框出的 / 标橙的 / 不用 / 改为 / 只有”。推不出来的，如实告诉 Owner，不要硬猜。
- **版面要宽。** 用独立的 HTML 页面：主栏约 960–1200px，加左侧目录。不用窄栏文档类型，原文里的宽幅图必须能看清。
- **改生成器，不手改 HTML。** 版式改动做在 `scripts/owner_pages/`，内容改动做在 `docs/owner/*.md`，然后重建。手改的 HTML 下次重建就没了。

## 2. 每一节 = 一条证据链（规范第 13.2 节）

1. 标题写成“问题：结论”，结论要有方向。
2. 记忆句 `p.memo`：一句话，带上决定结论的一两个数字。
3. 证据元素：**有数据就先放图**，图的标题就是结论；明细表放进“明细表”折叠区；一节最多展开一张表。
4. 读法：最多三条，每条以加粗短语开头。
5. 需要的话，加一句“下一节接什么”。

## 3. 元素规则

- **表格**
  - 列序就是阅读顺序：名字 → 证据（数字、条形）→ 原因（短语）→ 结论（标签）。
  - 必须有结论列，用标签表示（赢 / 输 / 兑现 / 不可用），不写长句。
  - 每一行在名字以外的格子里要有视觉重点：上色的数字、标签、内联条 `.ib`、大数字 `.big`。
  - 整张表只框一两格，也就是决定标题结论的那一格。整列都上色等于没有信息。
  - 单元格写短语，约 46 字以内；长理由放在表下或折叠区。
  - 长表用分组行 `tr.grp`，分组行本身就是一句小结论。
  - 名词表、清单表标 `data-lint="ref"`，但仍然要有焦点（见 3.5）。
  - 代码路径、PR、SHA 不进正文表格，放进“工程用”折叠区。
- **颜色语义全站统一**：绿 = 比参照好，橙 = 比参照差，框 = 决定结果的格子，标签 = 状态。同一版本在所有图里颜色相同。**颜色按每个数字自己的方向来定，不按页面的整体结论**：结论不通过，不等于页面上每个数字都标红。
- **正文**：不写没有加粗的大段文字。超过两行就拆成“加粗短语 + 解释”，或者做成卡片。判断类内容用结论卡片 `.vd-card`：大字结论 + 一两句证据 + 出处。
- **列表项**：都以加粗短语开头。
- **选项**：带建议的选项用卡片，推荐项高亮，写清每个选项的代价。
- **折叠区**：结构是 `div.fold > button.fold-h[aria-expanded] + div.fold-b`，必须实际点开验证过。
- **深色模式和窄屏（约 400px）**：都要检查。

## 3.5 焦点：每个大元素都要讲一句话

Owner 的标准是：**“加粗 + 纯文本”不合格**。每个大元素（页首、表格、卡片组、步骤、清单、总览）都要回答“到这里先看什么”，而且焦点只能取自源文档。下面的组件已经在 `scripts/owner_pages/story.py` 里实现，新页面直接套用。

- **页首（`section.status`）：结论放在最前面**，不要做成三张一样大的卡片。
  - 结论卡最大：第一句做成大字标题，其余作为灰色证据。
  - 能画就画：“策略 X% vs 基准 Y%”画成对比条；“N 个起点 K 个赢”画成 N 个圆点，赢的实心。
  - “需要你”放进单独的蓝框：动词放大，事项拆成 ①②③ 清单。不需要 Owner 操作时显示绿色的“✓ 不用操作”。
  - 进度降成一条细的状态栏：✓ 加一句话。
  - 愿景收成一行，目标加下划线，方便和结论对照。
- **步骤流（比如 4 步规则）**
  - 每张卡分三层：小灰字的步骤名 → 大号的焦点短语 → 原文解释。
  - 焦点取作者在这一步的加粗；没有加粗，就取这一步收尾的短句。
  - 每一步都取得到焦点才启用；几张卡的焦点连起来读，就是故事线。
- **决定记录（D 编号表）**
  - 顶部放一条按编号排序的时间线，节点能跳到对应卡片；最新的一条标“最新”。
  - 每张卡左栏写编号、名称、共几条；右栏用大号字写核心句。
  - 每条决定前加语义图标：
    - ✓ 规则；
    - ! 约束（只、不、推迟）；
    - ⇄ 替换旧做法：“不用 X”里的 X 加删除线；
    - ↻ 改动：“改为”标成旧 → 新；
    - ★ 结果：“只有 X 能…”里的 X 用绿色高亮。
- **接下来（行动表）**
  - 顶部一排计数：待你拍板、等你之后、待做、已完成、持续、排队。
  - Owner 的事项放进蓝框，做成编号的决定卡，动词放大；“A，或 B”拆成两个选项标签。
  - 其他人的事项做成并排的小卡，每条带状态标签：✓ 已完成 / ⏳ 等你拍板（正文写着“你定了…后”）/ → 待做 / ↻ 持续 / 排队。
  - D 编号、PR 号做成编号标签。
- **折叠区里的“这一段讲了什么”总览**：做成故事卡片，不要列表。
  - 每张卡有编号和结论标签（问题 / 有效 / 成立但有代价 / 背景），卡片顶边用同一种颜色。
  - 放大一个关键数字，从结论句里抽：A → B、A vs B、A … B，或涨跌两个数。
  - 下面是结论原文，数字高亮。
  - 没有结论句的小节改成带编号的跳转标签，不留空卡。
- **表格焦点（`table_focus`，所有表都适用，包括 `data-lint="ref"` 的表）**
  - 有“基准”列时，每个数字和同一行的基准比：好于基准绿底，差于基准橙底。回撤、波动、跟跌、换手这类指标越低越好。
  - 按表头决定列的角色：
    - 结论 / 判定 / 本该得出的结论 → 加左侧强调线，字体加重；
    - 为什么 / 证据 / 做了什么 → 灰色小字；
    - 代价 / 反面证据 / 超出就要查 → 橙色，表头加 ⚠；
    - 状态 / 可信度 → 状态标签；
    - “第 2 版 | 第 3.2 版”“上一轮 | 这次” → 旧版灰色，新版高亮，表头加 →。
  - 行首的 a / b / ① 编号做成小方块。
  - 只有 2–4 种取值的短分类列（设计前 / 设计期 / 检验前）做成彩色小标签。
  - “同上”换成上一格的标签（半透明），下面保留“同上”两个字。
  - 表头是“会不会变慢”这类问题时，“不会 / 会”做成好 / 差标签。
- **案例段落**：连续几行“X：一句话结论”，每行后面跟着正文的，做成并排的案例卡。X 做成标签，结论放大，按语义上色。
- **源文档里的行内子弹**：一行里有多个 `* ` 的，拆成子要点；有“A：”的，把 A 加粗。

## 4. 发布门（必须走完，不能跳过）

1. **自动检查**：`python scripts/owner_page_lint.py <page.html>` 必须 0 个 ERROR；WARN 逐条看，能改的就改。
2. **内容核对**：`python scripts/owner_pages/check2.py . docs/artifact`。源文档逐行和页面对照（去掉 Markdown 记号后做子串匹配）。图片张数一致，没有 `**`、`~~` 残留。剩下的差异只能是格式造成的。
3. **找纯文本元素**：`python scripts/owner_pages/audit.py docs/artifact`。它会列出没有视觉重点的表、没有数字或标签的卡片组、连续三段以上的纯段落，以及没有样式的长列表。要么清零，要么逐条说明原因。
4. **逐节截图**：用 `PAGES_DIR=docs/artifact python scripts/owner_pages/el.py out.png 'slug|selector|idx' …` 给每一节单独截图，然后写下三件事：① 标题的结论是什么；② 5 秒内能从哪个元素看到它；③ 视线先落在哪，再去哪。答不出 ② 就改。
5. **整篇通读**：只读标题和记忆句，看能不能连成一个完整的故事。
6. **逐屏看完整页**：先展开所有折叠区，等图片全部加载完再截图。不能只看一部分就说“审完了”。截图里如果整列都是同一个数，先怀疑生成器的变量作用域。
7. **改了公共组件，就重建并检查所有页面**：同一个类可能出现在别的页面上，比如 `.actboard` 也在 v4 体检报告里。只发布实际有变化的页面。
8. 规范第 12 节的八条照旧。

## 5. 发布与存档

- 用 artifact 发布：输出到临时目录（不设 `OWNER_PAGE_REPO`，图片会复制进各页的 `assets/`），再用 `publish_files` 发布 `index.html` 和 `assets/`。页面之间的链接互相指向新的 artifact（`scripts/owner_pages/links.json`），仓库里的文件链到 GitHub。
- 仓库存档：运行 `OWNER_PAGE_REPO=1 python scripts/owner_pages/build.py . docs/artifact scripts/owner_pages/links.json`，图片引用 `docs/assets/**`，不另存副本。
- 改版时，页面、仓库 md、项目空间三处要同步（规范第 10 节），`docs/artifact/` 也要同步重建。

## 5.5 处理 artifact 评论

- 先重读评论锚点所在那一节当前的 HTML，再动手。
- 改动做在生成器里。改完依次走：lint 0 个 ERROR → 内容核对 → 截图 → 发布 → 在评论线程里回复。回复里写清楚三件事：改了哪几层，焦点取自源文档的哪里，还有哪些页面跟着一起改了。
- 会话里只写一句话。线程留给人来关，不要自己 resolve。

**2026-11-17（评论轮次）**
- Owner 连续十几条评论都是同一个问题：**元素有样式，但没有焦点**。每个元素都要回答三件事：看哪里、为什么、和前后是什么关系。光有加粗、圆点、边框不算焦点。
- 焦点必须来自源文档：作者的加粗、结论列、和基准的比较、正文里的“不用 / 改为 / 只有”。不要自己发明评价。
- 数字格式化不能改动原值：4.0% 不能变成 4%，“年化”里的“年”不能被数字标签吃掉。
- 改生成器时注意变量作用域：在循环外用了上一轮循环的变量，导致整列显示同一个数（4.0%）。
- 嵌套的 wrapper 可能带来解释不清的偏移。能直接用 grid-area 排的，就不要多套一层。
