## 目标

以“用户与情境 → 任务 → 问题 → 证据 → 判断 → 行动或结束”为共同主线，设计并审查信息架构、视觉与交互。让需求、实现、测试及用户交付相互对应；不要把材料堆成界面。

## 输入与范围

确认目标用户、使用情境、核心任务、成功判据、平台约束、数据与证据来源、授权边界。先复用已有上下文与来源；仅对会改变工作方向的缺口提问。不要要求用户指定颜色或组件来代替任务定义。

## 工作流程

### 1. 定义任务和闭环

用一句话说明“谁在何时需要完成什么”。列出完成任务必须回答的问题。标记各模块承担认知、判断或行动哪种闭环；允许组合，但不要每块硬塞全部角色与全部问题。将无需操作的充分理解作为有效结束。

### 2. 规划信息架构

按理解和操作顺序组织，不按 PR、数据字段或材料来源组织。给每个模块填写：问题、核心答案、必要证据、下一步/终点、成功判据。区分主路径、支持解释和审计资料；关键限制不得折叠隐藏。使首屏能回答主问题，不以“信息完整”替代重点。

### 3. 选择视觉元素

先说清元素的职责再选形式。用卡片表达分组/状态/入口，用图揭示路径/比较/结构，用表支持同维度查找，用正文解释机制和判断。避免重复表达或把长段落塞进表格。保持色彩语义稳定，搭配文字或图标；不要仅凭颜色传意。让图展示过程、指标概括结果、表解释差异、文字给判断。

图表使用真实观测与明确派生，统一区间、单位、基准、成本和证据等级。缺失保持缺失；不从年化倒推曲线、不用正式数据冒充探索。调用适用的图表/文件技能完成绘制和验证，本 Skill 不替代工具规范。

### 4. 设计真实交互

对 Web/前端画出完整任务路径：入口 → 选择/输入 → 执行 → 反馈 → 下一步。覆盖加载、空、错误、权限不足、成功和恢复；按任务需要处理取消、重试和重复提交。风险操作提供后果提示与适当确认。不要为了“有UX”增加无必要点击；不要把静态卡片伪装成按钮。

对 Notion/报告采用清晰标题、阅读顺序、锚点、折叠和证据入口；说明平台不支持的交互，不宣称不存在的能力。

### 5. 连接开发与验收

维护轻量映射：用户任务 → 设计选择 → 实现范围 → 用例 → 可观察结果。区分单测通过、数字正确、交互可用与业务结论成立。仅在目标冲突、规则/权限改变或高风险时升级，不新增逐项 Owner 审批流程。

### 6. 验证与Review

按真实任务走查，不按组件逐项夸奖。核对入口、状态、认知负荷、证据口径、操作反馈、失败恢复、关键风险与最终完成。针对实现检查宽屏和约390px窄屏、键盘焦点与顺序、可访问名称、非颜色提示、对比度和适当触控目标；交互目标通常至少44×44px，正文对比度至少4.5:1。遵循所用平台/文件技能的渲染与验证要求；看实际输出，不把“已渲染”当成已检查。

将发现写为：严重性、位置、用户影响、缺失环节、建议修复、复验方法。区分设计建议、已实现与已验证。审查严重性：阻断任务/误导决策优先，其次额外认知或操作成本，最后美观细节。

### 7. 持续更新

先确定实质变化及其对判断/行动的影响，只修改相关模块。将PR、SHA、详细测试与历史日志放入工程记录，通过次级入口追溯。不以虚构完成百分比、漂亮曲线或压掉反例营造确定性。

## 交付要求

提供任务定义、模块职责、设计/实现产物、验证证据及未闭合项。交付实际页面或实现，不只给排版建议；依赖缺失时明确交付范围、阻塞物和恢复条件。不要在最终汇报重复整个规范。

## 正反案例

- 看板进度：用状态卡片呈现路线；展开区解释当前卡点的“问题—影响—解除条件—下一步”。不要在下方再重复一张长篇PR状态表。
- 投资图：收益与回撤相邻、颜色和日期一致；解释探索与正式结果差异。不要在正文选择E2、图里却只展示E1而不说明缺口。
- Web导出：验证用户真正获得正确文件，以及无数据/失败/重试；不要只确认按钮可点。
- Owner更新：说清变化对项目的影响及是否需要决定；不要用变基SHA和测试列表代替解释。

## 反向检查

逐个问：删掉它用户失去什么？保留它完成了什么职责？用户在哪一步仍需要猜？结论哪里缺证据？做完后哪里没有反馈或终点？不要把这份检查变成另一个内容堆积模块。
