先定义用户要完成的理解、判断和行动，再设计内容、界面与实现。不要把材料做成界面，要把任务设计成连贯的体验。

## 1. 一条贯穿始终的主线

**用户与情境 → 核心任务 → 必须回答的问题 → 必要证据 → 判断 → 行动或明确结束。**

将它贯穿需求、研究、信息架构、UI/UX、开发、测试、Review 和持续更新。不同阶段使用同一目标，不允许需求说用户价值、实现堆功能、验收只剩测试通过。

## 2. 三种闭环，不强迫每块同时具备

- **认知闭环**：读者知道发生了什么及为什么，不必拼接上下文。
- **判断闭环**：结论、依据、适用条件和不确定性相互对应。
- **行动闭环**：知道下一步能做什么、由谁做、何时停、成功或失败如何反馈。

给每个模块分配明确职责；模块之间衔接，不把所有角色的问题塞进每个模块。闭环不等于加按钮；了解后无需行动，也可以是明确终点。

## 3. 先定问题，再选表达

为每个模块先填写四项：

1. 谁会在什么情境下看它？
2. 看完必须明白、判断或完成什么？
3. 哪些证据和反馈足以支持这个任务？
4. 如何验证它真的帮助用户完成，而不只是内容齐全？

按用户理解和操作顺序组织，不按材料来源、数据库字段或开发事件顺序组织。先给结论与影响，再提供解释、证据和审计入口。关键风险不可藏在折叠区。

## 4. 信息价值不是信息数量

- 保留完整判断链，而非完整材料堆。删重复，不删改变结论的例外与局限。
- 区分成果、当前状态、剩余动作与阻塞；不以无依据的完成百分比制造精确感。
- 区分探索、正式实现、已核对、已批准和最终有效；不互相冒充。
- 维护面向用户的叙事与面向工程的证据两层：前者说影响和下一步，后者保留 PR、提交、测试与指纹。两者有链接，但不把审计材料摊在首页。
- 图、指标、文字共同回答一个问题：图展示路径，指标概括结果，表解释差异，文字给判断；不是四次重复同一信息。

## 5. 视觉与交互都要有职责

- 卡片用于分组、状态、优先级或入口，不因为“更好看”就把文字都装进去。
- 图表用于揭示变化、比较或结构。统一区间、单位、基准与证据等级；不得从年化推造曲线，不把缺失当零。
- 表格用于同维度精确比较与查找；没有共同维度的长段落不要硬塞进单元格。
- 颜色语义稳定，同时用文字/图标表达，不只靠颜色。
- 折叠用于次要解释与追溯；默认视图必须能独立回答主问题。
- 按钮与导航服务真实任务，提供清晰的当前位置、结果、失败原因与恢复路径。没有动作就不要假装可点击。

## 6. 从需求到开发的可追溯链

为每项能力维护一条轻量链：

**用户任务 → 设计选择 → 实现范围 → 验证用例 → 用户可观察的结果。**

功能存在、单测通过、数字正确、可用性合格、业务结论成立是不同层级。各自给证据，不能互相替代。不要把这套框架新增成逐项 Owner 审批门禁；只在目标冲突、权限、规则改变或高风险时升级。

持续更新时先回答：什么实质变化了？它改变了用户的哪个判断/行动？只更新受影响模块与证据入口；不要把增量日志不断堆到主页面。

## 7. Review：按任务走一遍，而不是按组件点名

检查以下问题，并把发现写成“位置 → 用户影响 → 缺失环节 → 修复 → 复验”：

- 用户能否找到入口，知道此刻的位置和状态？
- 是否需要猜缩写、拼上下文、来回查表才能理解？
- 结论是否有相同口径的证据，例外会否改变结论？
- 操作是否有反馈、错误是否能恢复、重要风险是否提前呈现？
- 删除一个元素后用户会失去什么？保留后它是否完成了职责？
- 桌面、窄屏、键盘与辅助技术下，主任务是否仍成立？

## 8. 两个迁移案例

**Owner 看板**：进度回答“走到哪、卡什么、接下来去哪”；投资证据回答“怎样赚钱、怎样亏钱、为什么选这个方案”；决策区回答“是否需要我、有什么选择及代价”。PR 流水账不承担这些解释。

**Web 导出流程**：用户要拿到可用文件，不是“点击导出按钮”。界面要覆盖入口、范围与格式、运行状态、成功下载、空数据、失败重试及返回路径。验收用这条完整任务链，不只检查按钮出现。

## 使用边界

将本框架作为设计与验收方法，不替代项目合同、研究纪律、数据口径或授权。适用工具受限时给出可行降级，并标明未验证部分，不声称已实现不存在的交互。
