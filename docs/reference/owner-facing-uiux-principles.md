## 0. 这份文档是什么

它是这几轮改版中 Owner 实际提出的要求和判断标准的沉淀。抽象的方法框架（“任务 → 问题 → 证据 → 判断 → 行动”）只是起点。本文写的是在本项目里，怎样才算做到了这一点。后续做 Web 端时，页面结构、组件和文案都按本文执行，保证看板和 Web 端是同一套理念。

一句话：**UX 下大力气，UI 做到常规水准。** 让人读得舒服、看得明白，比好看更重要。

### 0.1 注意力与减熵（Owner 2026-11-01，每次更新都不能松懈）

注意力是最稀缺的资源。讨论和迭代会自然地制造信息熵：版本说明、过时的章节、重复的状态、同一个数字出现在三个页面。文档的职责是减熵，让读者的注意力落在重点上。基准样例：《v4 体检报告》的过关表（结论列、只给关键格子上色、决定结果的格子加框）。

- **一节一问。** 标题加第一句话就是答案；一节想回答两个问题，就拆开或删掉一个。
- **五秒测试。** 只看标题、记忆句和被强调的格子，就能知道这一节在说什么；其余都是证据。
- **表格要有结论。** 比较表必须有结论列或状态标签；颜色只给和参照不同、而且影响结论的格子，框只给决定结果的一两格。整列都是同一种颜色，等于没有信息。
- **单元格是短语，不是段落。** 长的理由放到表下一行说明，或者收进折叠区。
- **只写现状。** 旧版本、早先的计划、修复记录、被取代的分析，进更新记录、标“留档”的折叠区或 git。每次更新都清理过时的“需要你”和“下一步”。
- **一件事只在一处展开。** 其他页面链接过去。看板是其他页面的索引，不是副本。
- **所有页面同一套视觉语言。** 绿 = 比参照好，橙 = 比参照差，框 = 决定结果的格子，标签 = 状态（做 / 不做 / 待批 / 以后）。等你批准的事项在所有页面用同一个“待批”标签。
- **收尾的版本变成留档。** 页首用一张小表写清结局，标“留档”，过时的路线和决定收进折叠区。

### 方法框架（并入自 PR #46，D11-7）

- **一条主线贯穿始终**：读者与情境 → 核心任务 → 必须回答的问题 → 必要证据 → 判断 → 行动或明确结束。需求、设计、开发、测试、评审、更新都对着同一条主线，不允许需求讲用户价值、实现堆功能、验收只剩测试通过。
- **三种闭环，按模块分配**：认知闭环（知道发生了什么、为什么），判断闭环（结论、依据、适用条件、不确定性对得上），行动闭环（知道下一步、谁做、何时停、成败如何反馈）。看完不需要行动，也是一种明确的结束。
- **先定问题，再选表达**：每个模块先写清楚谁在什么情境下看、看完要明白或完成什么、哪些证据足够、怎样验证它真的帮到了人。
- **可追溯链**：读者任务 → 设计选择 → 实现范围 → 用例 → 可观察结果。区分“测试通过”“数字正确”“交互可用”“业务结论成立”，四者不能互相冒充。
- **评审按严重性排序**：先看阻断任务或误导决策的问题，再看额外的认知或操作成本，最后看美观细节。每条发现写清位置、对读者的影响、建议修复、如何复验。

## 1. 先定读者，每个模块自成闭环

- 看板有三种读者视角：**技术经理**看进度，**基金经理**看策略到底行不行，**产品经理**看整份文档的结构、交互和措辞。
- 不是每个模块都要照顾三种人。每个模块有一个主要读者，这个读者读完就不用再往别处找。闭环 = 他关心的问题 + 证据 + 结论 + 对他意味着什么（下一步，或者明确“不用做事”）。
- 反例：进度卡片很好，展开的表格却是内容堆砌，看不出重点。卡片和表格讲的是同一件事，却没有连成一个闭环。

## 2. 每一条事项都要有头有尾

任何需要 Owner 知道或决定的事项，都写成一张卡片，包含三块：

| 块 | 写什么 | 反例 |
| --- | --- | --- |
| **发生了什么** | 用大白话从头讲：规则原本怎么写、遇到了什么情况、哪里没写清 | “缺价那天的离场单怎么成交”，没有前因，读者不知道缺的是什么价 |
| **影响有多大** | 对数字、结论、愿景的实际影响，能量化就量化（“10 年里一次都没碰上”） | 只写“需要处理” |
| **你要做什么** | 标签只用两种：**要你选**（给出选项和建议）／**不用你做事**（写明谁来做） | 写“你确认”，却不说确认什么 |

- 读者看不懂的事项，只能交给别人看着办，信息从这里开始变成黑盒。宁可多写一句来龙去脉。
- 需要决定的事，把选项摆出来，标明建议和每个选项的代价，并且只留真正需要 Owner 判断的选择。

## 3. 阅读顺序必须自洽（被动 UX）

UX 不只是点击之后的反馈。布局、元素的先后、正文的写法，都在决定读者能不能顺着读下去。

- **先讲是什么，再讲区别**：先用一句话说明策略在做什么，再讲选法，最后讲各版本。不要先摆出版本卡片，让读者看完卡片还要往下猜“原规则”指的是什么。
- **先给结论，再给证据**：每节开头是一句能记住的话，接着是图，图下最多三条读图要点。
- **没有信息量的段落就删**：如果一段话只是指向后文（“见 3.6”），就移到它该在的地方。
- **定义要放在用到之前**：图表里出现的版本名，读者在看图之前就应该认识。

## 4. 给读者留记忆点

- **每节一句记忆句**：短、具体、带数字，例如“2006 年沪深300 涨了 125%，v3 有 60% 的钱拿着现金”。用醒目的样式放在节首。
- **版本要有外号，并且全文统一**：`v3 · 原规则`、`E1 · 补全池子`、`E2 · 补全池子 + 10% 离场`、`C1 · 快信号回场`、`C2 · 门槛看 60 日`。只写代码（v3、E1）太干，读完记不住它是什么。
- **“只改一处”要被看见**：每个版本卡片标出“改一处”，并高亮改动的那几个字。对比两种规则时，用“原规则划掉 → 新规则高亮”的写法，让人一眼看出改了哪里。
- **一个版本 = 一行定义 + 一个结果 + 一句评价**：卡片里同时放年化和回撤的大号数字、相对基准的小条形，以及一句好坏评价（“跑输基准，因为……”）。

## 5. 数字是正文里信息最集中的地方

- 关键数字一律加粗，并且**按含义上色**：好 = 绿，差 = 橙或红，基准 = 黑，中性 = 灰。颜色的含义全文固定，同时有文字说明，不只靠颜色传达。
- 同一个数字在全文只用一种写法和口径。不同口径的数字（探索版与正式版）必须标明来源，不能互相冒充。
- 表格里比对照组好的格子标绿，差的标橙，读者不用逐格比较。

## 6. 图表

- **标题就是结论**，不写“净值对比”这类名词标题。
- 图例使用版本外号，颜色和定义区一致；同一个版本在所有图里颜色相同。
- 线尾直接标出终值、**总收益和年化**；回撤用共享时间轴的副图，并标出各自的最深点。
- 把关键数字和解释直接写在图上，例如“2006：沪深300 +125%，v3 60% 现金”，不要让读者在图和正文之间来回对照。
- 一张图只讲一件事。需要比较两种状态时，用左右并排的小图，不用一条看两遍才懂的叠加折线。
- 比例刻度从合理的零点开始，不用截断的坐标夸大差距。
- 只用真实数据。缺失就标为缺失，不从年化倒推曲线；重建的曲线要注明怎么重建、和原记录差多少。

## 7. 看板不是工作日志

- 更新只写**对 Owner 有意义的变化**：哪个判断变了、对愿景意味着什么、下一次什么时候需要他。
- PR 编号、提交号、复审往返、测试列表等开发流水，放进 `operations/` 的工程记录，看板最多给一个入口。
- 不用内部编号（G2、§4.5.6、B1）代替解释；必须出现时，在旁边用一句话说明它是什么。

## 8. 深度：写到决策需要的程度为止

- 太细（把证据底稿搬上看板）和太简（只给结论、删掉证据链）都是失败。
- 合适的深度：每个结论下面留够让基金经理信服的证据，例如参数是否是一片平台、前后两段是否都成立、反例在哪里。
- 次要的解释和审计资料放进折叠区；但关键限制和风险不能折叠。
- 改版时不能删掉 Owner 以前问过、仍然有效的内容，比如历史问答，可以移到折叠区。

## 9. 主动回答“为什么”和“能不能改”

- 出现失手或异常时，要回答三件事：**原因是什么**（拆到机制，用数据证明）、**能不能改**（给出按机制设计的候选，并实测）、**如果不能，为什么**（是工具限制还是信号问题）。
- 只说“这是代价”“盈亏同源”不够。要把账算全（例如把 2008、2009 两年合起来看），再给出改进方向和证据强度。
- 回应 Owner 的质疑时，先判断他说得对不对，对就直接说对，再补充他没看到的部分。

## 10. 交付形式

- 给 Owner 看的东西，交付为能直接打开的带图页面（Claude 页面）；仓库里保留同内容的 md 镜像，供开发和历史追溯。
- 每次改版，三处同时更新：页面、仓库 md、项目空间。
- 仓库 md 的样式和页面一一对应：记忆句和结论框用引用块，顶部状态、事项卡片、版本卡片、选项用表格，步骤用编号列表，规则改动用“原规则（删除线）/ 新规则”表格，折叠区用 `<details>`。转换脚本：`results/v3/diag/2026-10-27-owner-board/tomd3.py`。

## 11. 移植到 Web 端：组件对照

| 看板里的形式 | Web 端组件 | 职责 |
| --- | --- | --- |
| 顶部三格（工程进度 / 业务结论 / 需要你） | 状态摘要条 | 首屏回答“现在怎样、要我做什么” |
| 路线图卡片 | 进度时间线 | 技术经理视角的完整路线，红色表示阻塞、紫色表示需要 Owner |
| 事项卡片（发生了什么 / 影响 / 你要做什么） | 待办 / 决策卡片 | 每条事项自成闭环；“要你选”的卡片里直接放选项 |
| 记忆句 + 图 + 三条要点 | 洞察区块 | 结论在先，证据在后 |
| 版本卡片（外号、改一处、条形、数字、评价） | 策略版本卡片 | 一眼比较优劣 |
| 规则差异卡（划掉 → 高亮） | Diff 组件 | 显示改动 |
| 数字语义色 | 设计令牌 `--good / --bad / --bm / --muted` | 全站统一 |
| 折叠区 | 可展开面板（按钮 + aria-expanded） | 次要解释与审计入口 |

Web 端额外要求：完整任务路径（入口 → 操作 → 反馈 → 下一步），覆盖加载、空、错误、成功四种状态；不把静态卡片伪装成按钮；可点的东西必须真的能点，并且在发布前实测（本看板曾经出现过折叠块点了没反应）。

## 12. 发布前自查

1. 每个模块的主要读者是谁？他读完还需要去别处找吗？
2. 每条需要 Owner 知道的事项，有没有“发生了什么 / 影响 / 你要做什么”？
3. 从上往下读，每个名词在第一次出现之前有没有被解释？
4. 每节有没有一句记忆句？关键数字有没有按含义上色？
5. 每张图的标题是不是结论？图例和定义区一致吗？
6. 有没有开发流水混进来？有没有内部编号没解释？
7. 有没有删掉 Owner 以前关心、仍然有效的信息？
8. 所有可点击的元素实测过吗？窄屏（约 400px）和深色模式检查过吗？

## 13. 叙事和表格的硬规则，以及发布门（2026-11-05，Owner 多次指出同一类问题后加）

### 13.1 为什么前面的规则不够

第 0–12 节写的是“要做到什么”，但没有写“表格具体长什么样”，也没有一道真正拦得住的门。结果每次都是：先把内容写成纯文字表格，再用第 12 节自查打勾。第 12 节的问题都能凭印象回答“是”，所以拦不住。《第二阶段复盘》第 1 版就是这样：表格有代码列、没有结论列、每行都是纯文字，第 5 节的表和标题对不上。

### 13.2 一节 = 一条证据链

每节按这个顺序写，缺一环就不发布：

1. **标题 = 问题：结论**，结论里有方向（“只有 A2 兑现了”“最大一块是美股”）。
2. **记忆句**：一句话，带决定结论的那一两个数字，数字按含义上色。
3. **证据元素**：图、表或卡片。读者扫 5 秒，必须能从它上面**直接看到**标题里的结论（结论列的标签、框出的格子、最长的条）。
4. **读法**：最多三条，每条以加粗短语开头。
5. 需要的话，留一句“下一节接什么”。

### 13.3 表格的样式（组件见 `docs/reference/owner-page-story.css`）

- **列的顺序就是阅读顺序**：名字 → 证据（数字、条）→ 原因（短语）→ 结论（标签）。读者从左到右读，就是一句完整的话。
- **必须有结论列**：用标签（赢 / 输 / 兑现 / 不可用），不是一句长话。
- **每一行都要有视觉重点**，而且落在名字以外的格子里：上色的数字、标签、内联条、大数字。第一列加粗不算。
- **整张表只框一两格**：决定标题结论的那一格。
- **单元格是短语**：不超过约 40 个字；长理由放到表下“读法”，或者折叠区。
- **长表要分组**：用分组行（`tr.grp`）把行按结论分成两三组，分组行本身就是小结论（“看见了，没行动”“没去查”）。读者不用读完每一行就知道结构。
- **跨节呼应**：同一件事在几节里出现时，用同一个字母或编号标记（`<span class="lt">a</span>`、`①`），后面的节用标记回指，不重复展开。
- **数字的大小要能看出来**：比较大小的列用内联条（`.ib`），差距大的格子加框。
- **工程信息不进正文表格**：代码路径、冻结标签、PR、SHA 放进折叠区“工程用”。

### 13.4 正文

- 不写没有加粗的大段文字。超过两行的段落，要么拆成“加粗短语 + 解释”的列表，要么变成卡片。
- 判断类内容（成立 / 不成立、靶子 ①②③）用结论卡片（`.vd-card`），卡片上是一个大字结论 + 一两句证据 + 一行出处。

### 13.5 发布门（必须走完，不能跳过）

1. **自动检查**：`python scripts/owner_page_lint.py <源.html>`，0 个 ERROR 才允许构建（构建脚本会先跑它）。WARN 逐条看，能改就改。
2. **逐节截图复核**：每节单独截图，逐节写下三件事再发布：① 标题的结论是什么；② 5 秒内能从哪个元素看到它；③ 读者的视线先落在哪里、再去哪里。任何一节答不出 ②，就改到答得出。
3. **整篇通读一次**：从上往下只读标题和记忆句，能不能连成一个完整的故事。不能，就调整节的顺序或标题。
4. 第 12 节的八条照旧。

### 13.x 先图后表（Owner 2026-11-06）
